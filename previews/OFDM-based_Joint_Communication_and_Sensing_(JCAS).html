OFDM-based Joint Communication and Sensing (JCAS)

Aus der lokalen IHF-Wiki-Sandbox
Zur Navigation springen Zur Suche springen

The OFDM-based Joint Communication and Sensing (JCAS) project develops a GNU Radio system in which one OFDM waveform carries data and provides channel measurements for sensing. The intended application is a quasi-bistatic automotive scenario with a transmitting and sensing node and a separate communication receiver.

Project scope and status

The project covers an OFDM communication link, channel-response processing for sensing, and deployment on the NI USRP-2954R. The current repository contains a reproducible channel-model simulation. Hardware adaptation and quantitative sensing validation remain separate development tasks.

“Performed” in this table reports the project record; it is not a substitute for measurement data. Use the repository history and test records when a numerical result or completion decision is required.

Intended system architecture

The planned primary node uses one UBX-160 daughterboard for transmission and the other for sensing reception. A second USRP acts as the communication receiver; its exact hardware configuration is not defined in the current repository. Both daughterboards on the primary USRP have been checked in transmit and receive configurations. Their final roles should be assigned only after comparable measurements have been recorded.

Primary node                                  Communication node

payload -> OFDM TX -> RF waveform -----------------------------> OFDM RX -> payload
                       |
                       +-> target / propagation -> sensing RX -> CFR -> CIR / DDM

The main repository flowgraph does not yet implement this complete hardware diagram. It connects the transmitter to a software channel model and then to one receiver; there are no UHD Source or UHD Sink blocks in that graph.

Why OFDM can support both functions

OFDM divides the occupied bandwidth among orthogonal subcarriers. Data symbols are transmitted in parallel, while known preambles and pilots support synchronisation and channel estimation. A cyclic prefix copies the end of each OFDM symbol to its beginning, which reduces inter-symbol interference when it is longer than the relevant channel delay spread.

For communication, the receiver estimates the channel, equalises the data carriers, and decodes the payload. For sensing, the same received frame is compared with an estimate of the transmitted subcarrier symbols. Variation across subcarriers represents delay-dependent channel structure; variation across successive OFDM symbols represents Doppler-dependent structure. The two branches therefore reuse the same waveform, but they need different validation criteria.

Current simulation signal chain

repeating byte ramp -> packet tagging -> OFDM transmitter -> channel model -> OFDM receiver
        |                                                           |
        +-------------------- transmitted PDU -----------------------+-> decoded PDU -> BER
                                                                    |
                                                                    +-> active-carrier symbols
                                                                         -> CFR -> CIR / DDM

The reference launchers generate seven repetitions of the byte values 0 to 255, giving a 1792-byte payload. A Throttle block controls the software-only simulation. It must be removed when the graph is replaced by hardware sources or sinks.

OFDM frame

The transmitter uses a 128-point inverse FFT. Of the 128 bins, 127 are active: 115 carry header or payload data and 12 are pilots. The Nyquist bin is unused. The current pilot bins are -55, -45, -35, -25, -15, -5, 5, 15, 25, 35, 45, and 55, with pilot value 1.

Both header and payload use QPSK, and scrambling is disabled in the main flowgraph. The frame begins with two synchronisation words:

  • the first is a Zadoff–Chu sequence placed on alternating active carriers, producing the repeated time-domain halves used by the synchroniser; and
  • the second is a fixed-seed BPSK sequence used for channel estimation.

After the header and payload symbols are assigned to carriers, the transmitter performs the inverse FFT and adds the cyclic prefix.

Simulated channel

Flow_graphs/Channel_Model.grc adds three copies of the signal and complex Gaussian noise. The direct copy has zero delay and scale factor 1. The other copies are delayed by 20 and 40 samples, scaled by 0.2, and multiplied by 200 Hz and 100 Hz complex sources respectively. Those sources have amplitudes 0.3 and 0.2. The Gaussian-noise amplitude is 0.001.

These values are diagnostic simulation settings, not a calibrated vehicular channel model. The channel hierarchy has its own fixed 100 kS/s rate parameter. A change to the top-level sample rate must therefore be checked against the channel hierarchy and its Doppler-source timing.

Receiver

The custom receiver has two inputs and three outputs.

PortStreamUse in the main graph
Input 0Complex received samplesSynchronisation, header recovery, payload recovery, and sensing-symbol extraction
Input 1Float frequency-correction controlConnected to a constant zero in the current simulation, so the correction oscillator applies no fine-frequency adjustment
Output 0Decoded bytesReceived-data display and PDU-based BER calculation
Output 1Serialised, unequalised active-carrier samplesReceived-symbol term in the CFR calculation; the main graph first scales it by 1/N
Output 2Softly equalised active-carrier samplesEstimate of the transmitted active-carrier symbols used in the CFR denominator

The synchroniser uses the repeated halves of the first preamble and triggers on the falling edge of its correlation metric at a threshold of 0.996. A header/payload demultiplexer separates the frame. The two preambles initialise the channel estimate; the payload branch uses a decision-feedback equaliser with adaptation factor 0.1. The main graph currently leaves the external fine-frequency correction input at zero because applying the estimated correction caused unstable DDM behaviour in the assumed synchronised simulation.

Communication branch

The receiver reconstructs packed payload bytes. The BER block converts transmitted and received tagged streams to PDUs, matches them by the recovered packet_num, counts differing bits, and reports cumulative bit errors divided by cumulative compared bits.

This BER value describes only packets that reach the comparison block. Packet loss, acquisition failure, and unmatched packets need separate accounting in a complete link evaluation.

Sensing branch

For each active subcarrier k and OFDM symbol m, the graph forms a channel-frequency-response estimate of the form:

H[k,m] = (Y[k,m] / N) / X_est[k,m]

Here Y is the unequalised receiver output, X_est is the softly equalised estimate of the transmitted active-carrier symbol, and N is the configured number of active carriers. The samples are assembled column by column into an N × M matrix. A truncation block retains either all M symbols or the first M-1, according to M_crop.

ProductCurrent calculationCurrent display
Channel frequency response (CFR)Element-wise received/reference ratio on the active carriersReal part of the N × M_crop matrix
Channel impulse response (CIR)Orthonormal IFFT of the CFR along the subcarrier dimensionReal part of the N × M_crop matrix
Delay-Doppler map (DDM)Configurable two-dimensional window, zero-padding, IFFT across subcarriers, FFT across symbols, then magnitude squaredLinear magnitude-squared view and a view converted with 10 log10

The resolution factor controls zero-padding and display sampling; it does not improve the physical delay or Doppler resolution of the waveform. CFR and CIR windows show only the real component, not magnitude. The DDM values are processing outputs and are not calibrated received power, radar cross section, or detection probability.

The launchers do not pass a carrier frequency to the DDM visualisers. In that mode the horizontal increment is calculated as a simulated Doppler frequency, although the window still labels the axis as velocity in m/s. A physical velocity interpretation requires a non-zero carrier frequency and validation of the complete axis calculation.

Running the simulation

The reference environment is GNU Radio 3.10.x; the repository records 3.10.12.0. Python, NumPy, SciPy, pyzmq, PyQt5, pyqtgraph, and SIP must be available in the same environment.

On Linux:

git clone git@git.rwth-aachen.de:ihf/sdr/jcas-ofdm.git
cd jcas-ofdm

./Simulation_starter.sh --check
./Simulation_starter.sh

Activate the intended Conda or Radioconda environment first if GNU Radio is not installed system-wide. PYTHON_BIN and GRCC_BIN can select explicit executables. On Windows, set the local Radioconda activation path near the start of Simulation_starter.bat, then run the batch file.

The Windows launcher compiles against the custom block definitions installed in its GNU Radio environment. Unlike the Linux launcher, it does not repair the legacy definitions in Block_definition/ at launch time. Before relying on the Windows path, confirm that the installed transmitter and receiver definitions use the current class names and expose the receiver's complex-sample and float-correction inputs.

A normal run should show received data and BER in the GNU Radio window and open separate CFR, CIR, DDM dB, and DDM linear windows. Check for import, compilation, port-binding, vector-size, and flowgraph errors before interpreting the plots.

The plotters write binary diagnostic files under Raw_data/. They overwrite their respective file at startup and can grow during long runs. Use --no-diagnostics with the Linux launcher when those captures should be removed at shutdown.

Hardware verification and development priorities

Detailed procedures and result records belong in docs/First_tests.md. At overview level, the sequence is:

  1. verify host connectivity and streaming;
  2. compare both transmitter RF chains;
  3. compare both receiver RF chains;
  4. verify the timing and frequency relationship needed between daughterboards;
  5. establish pure OFDM communication;
  6. validate sensing with a known static scene; and
  7. demonstrate joint communication and sensing over the air.

The most important next steps are to preserve complete measurement records, select the primary-USRP TX and sensing-RX roles from comparable data, connect a controlled UHD hardware path, verify synchronisation, and calibrate the sensing axes and levels against known delay and Doppler cases. Only then should static-target and joint over-the-air results be described as validated.

The committed custom-block definitions and generated main Python graph also need to be regenerated from, and aligned with, the current GRC and hand-written receiver. The Linux launcher works around the legacy definition names and missing float input in temporary files; that workaround should not be mistaken for source consistency.

Communication evaluation should distinguish BER on matched packets from acquisition failures and lost packets. Candidate measures include EVM, spectral efficiency, and peak-to-average power ratio. Sensing evaluation should cover measured delay and Doppler resolution, unambiguous regions, sidelobes, processing gain, and detection performance. These are evaluation goals; they are not all current program outputs.

Interpretation limits

  • A screen level is not absolute RF power unless the full path and display scaling have been calibrated.
  • A simulated peak is not a detected target; the current graph has no detector or false-alarm control.
  • Zero-padded bins make a plot smoother but do not create physical resolution.
  • A successful communication decode does not prove that sensing timing, phase coherence, or axes are correct.
  • Hardware sample rates and the reference simulation rate are different configurations and must not be mixed in a result.
  • Every quantitative result should identify the code revision, waveform parameters, channel or RF setup, reference plane, normalisation, and known limitations.

Continuing the project

Start with README.md for orientation, then read MAINTENANCE.md, the main GRC files, OFDMJCAStxrx.py, and the current test document. Work on a focused branch, run the Linux preflight or the corresponding Windows checks, and compare the observed frame sizes and peaks with the configured channel before opening a merge request.

When the implementation changes, update the source-of-truth file first. Keep block definitions, stream signatures, coupled parameters, launcher defaults, plot vector sizes, ports, and documentation consistent. Do not commit generated captures, local environment paths, or Python caches.
