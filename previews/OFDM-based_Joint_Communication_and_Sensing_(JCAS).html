OFDM-based Joint Communication and Sensing (JCAS)

Aus der lokalen IHF-Wiki-Sandbox
Zur Navigation springen Zur Suche springen

The OFDM-based Joint Communication and Sensing (JCAS) project develops a GNU Radio system that uses one OFDM waveform for data communication and environmental sensing. The intended application is a quasi-bistatic automotive scenario in which nodes exchange data while estimating target range and velocity.

Objectives

  • Implement an OFDM transmitter and receiver in GNU Radio.
  • Decode the communication payload and evaluate communication performance.
  • Estimate the channel frequency response (CFR), channel impulse response (CIR), and delay-Doppler map (DDM) for sensing.
  • Deploy the processing chain on USRP hardware near 5.8 GHz.
  • Evaluate trade-offs between communication and sensing parameters.

System architecture

The primary USRP uses different UBX-160 daughterboards for transmission and sensing reception. A second receive node represents the communication partner and supports the quasi-bistatic scenario.

Payload -> OFDM transmitter -> channel or RF link -> OFDM receiver -> decoded payload / BER
                                  |                      |
                                  |                      +-> received OFDM symbols
                                  +--------------------------> CFR -> CIR and DDM

The main repository flowgraph is a simulation using a channel model. It does not control the USRP. Hardware measurements require a separate UHD-connected flowgraph and the precautions described on NI USRP-2954R and UBX-160.

Software requirements

  • GNU Radio 3.10; the repository reference version is 3.10.12.0.
  • Python 3 with NumPy, SciPy, pyzmq, PyQt5, pyqtgraph, and SIP.
  • Git for source control.
  • UHD for USRP-connected measurements; UHD is not required for the channel-model-only simulation.

Running the simulation

Clone the repository and run the preflight check before starting the full simulation.

git clone git@git.rwth-aachen.de:ihf/sdr/jcas-ofdm.git
cd jcas-ofdm

./Simulation_starter.sh --check
./Simulation_starter.sh

For a Radioconda or Conda installation, activate the environment first. On Windows, configure the Radioconda activation path in Simulation_starter.bat and start that launcher instead.

The run should open the GNU Radio window and separate CFR, CIR, DDM dB, and DDM linear views. Verify that received data and BER update, all plotters receive complete frames, and no process reports import, compilation, port-binding, or vector-size errors.

Main simulation parameters

ParameterMeaning
samp_rateSimulation sample rate; this is not the USRP hardware sample rate
NNumber of active OFDM subcarriers
MNumber of OFDM symbols per frame
M_cropNumber of symbols retained for sensing processing
cp_lenCyclic-prefix length
resolZero-padding/resolution factor used by the sensing visualizers

The default simulation uses 100 kS/s. The initial USRP RF tests use a 200 MHz master clock and 100 MS/s. Keep these configurations separate and always state which one a result uses.

Outputs and evaluation quantities

AreaCurrent outputsAdditional evaluation quantities

Do not treat uncalibrated display levels as absolute RF power or radar cross section. Every quantitative result must state its signal path, reference plane, normalization, sample rate, and processing settings.

Hardware verification

The repository test document separates hardware checks from application-level integration:

  1. USRP and host streaming throughput
  2. Transmitter RF-chain characterization
  3. Receiver RF-chain characterization
  4. Inter-daughterboard synchronization
  5. Pure OFDM communication
  6. Pure sensing with a static target
  7. Joint communication and sensing over the air

Use docs/First_tests.md in the repository for the detailed and current procedures. Store raw results, scripts, and figures with the version-controlled project material rather than duplicating changeable procedures on this overview page.

Documentation policy

This page provides the stable project overview. The GitLab repository remains the source of truth for source code, exact parameters, setup procedures, test status, and results. When behavior changes:

  1. update and verify the repository documentation;
  2. merge the code and documentation together; and
  3. update this page only when the architecture, entry points, hardware, or links change.
